## DM 指南导入功能（阿里云 OSS 分片上传）

需求：导入 ~400MB 的 PDF，OSS 分片上传，生成链接发后端，文件 7 天生命周期。

### 关键决策（用户确认）
- 运行端：**H5 为主 + 小程序降级提示**。原因：小程序 `chooseMessageFile` 只能从聊天记录选文件，
  微信聊天本身传不了 400MB；`request` 单包上限 10MB 且拿不到响应头 ETag。
- 鉴权：**后端签发分片预签名 PUT URL**，前端零密钥。
- 后端接口尚未定，由前端出契约，全部集中在 `src/constants/upload.ts`。

### 新增文件
- `src/constants/upload.ts` — 分片 5MB / 并发 4 / 重试 3 / 每批签名 20 / 上限 500MB / 前缀 `dm-guide/`
- `src/services/request.ts` — Taro.request 封装（ApiResponse<T> + ApiError）
- `src/services/dmGuide.ts` — init / part-urls / complete / abort / records 五个接口
- `src/utils/ossMultipartUpload.ts` — 分片引擎：并发池、指数退避重试、进度节流200ms+EMA测速、断点续传、取消
- `src/utils/filePicker.ts`、`src/utils/format.ts`
- `src/components/ImportDmGuide/` — 按钮 + 进度浮层
- `docs/dm-guide-upload-api.md` — 接口契约 + OSS 配置说明
- 改动：`src/pages/index/index.tsx`、`index.less` 接入按钮

### 技术坑点（务必记住）
1. **OSS CORS 必须把 `ETag` 加进 ExposeHeaders**，否则前端读不到 ETag，合并分片必失败。代码里已针对此给出专门报错文案。
2. 预签名 URL **签名不能包含 Content-Type**；`file.slice()` 出的 Blob 无 type，XHR 不会自动附加该头，手动加头会 SignatureDoesNotMatch。
3. 分片上传用原生 XHR 而非 Taro.request：需要 `upload.onprogress` 和 `getResponseHeader('ETag')`。
4. 400MB 必须用 `file.slice()` 流式交给 XHR，**绝不能用 FileReader 读整个文件**（爆内存）。
5. 文件 7 天过期只能在 **Bucket 生命周期规则**配（前缀 `dm-guide/`），前端无法为单对象设置。
   同时必须开启「删除未完成的分片上传」碎片清理，否则用户中途关页面留下的碎片会一直计费。
6. 分批签名（每批 20 片）而非一次性签完，避免大文件传到后半程签名过期。

## ossMultipartUpload.ts 重构（对齐后端 task_id 四步流程）

用户要求专门重构一次 `ossMultipartUpload.ts`。背景：之前是我单方面出的契约（uploadId/objectKey + 本地 localStorage 断点续传），
实际后端 `/auth/*` 之外已有完整 `/uploads/*` 接口，是 **task_id 驱动**的。重构把前端引擎对齐到后端真实流程。

### 后端真实链路（已在 live 后端用 12MB/3 分片文件跑通验证，全流程 11 项检查通过）
1. `POST /uploads/temp/init`（uploadType=temporary）→ 返回 `task_id, chunk_size, total_parts, instant, resumed, uploaded_parts[], file?`
2. `POST /uploads/{task_id}/presign`（分批，每批 SIGN_BATCH_SIZE=50）
3. `PUT <oss-url>` 浏览器直传（**不带 Content-Type**，否则 403 SignatureDoesNotMatch）
4. `POST /uploads/{task_id}/parts/callback` 仅审计可忽略失败
5. `POST /uploads/{task_id}/complete`（body 仅 `{verify_size:true}`，**不含 parts**）→ 返回 `FileInfo`（无 URL）
6. `GET /files/{file_id}/download-url` → 才拿到带签名的可访问链接（注意：预签名 URL 是 method 绑定的，HEAD 会 403，必须用 GET）

### 文件改动
- `src/constants/upload.ts`：删 uploadId/objectKey 模型，改为 task_id 路径构造；并发 4 / 重试 3 / 每批签名 50 / 上限 500MB。
- `src/services/upload.ts`（**新**）：接口层，类型镜像后端 pydantic（保留 snake_case 以便编译期发现漂移）。
- `src/utils/fileHash.ts`（**新**）：抽样 SHA-256 指纹（头/中/尾各 2MB + 文件大小，≤6MB 全量；无 crypto.subtle 时 FNV-1a 兜底），失败返回 '' 不阻断上传。
- `src/utils/ossMultipartUpload.ts`（**重写**）：核心引擎，新增 `hashing`/`finishing` 阶段；用服务端 `chunk_size` 切片；服务端断点续传；秒传短路；complete 缺片自愈（409 incomplete_parts + missing_parts 自动补传，最多 MAX_COMPLETE_REPAIR_ROUNDS=2 轮）。
- `src/components/ImportDmGuide/index.tsx`：onSuccess 改为 `(result: UploadResult) => void`，去掉 submitDmGuideRecord（被 complete+download-url 取代）。
- `src/pages/index/index.tsx`：onSuccess 仅 console.log。
- `src/services/dmGuide.ts`（**删除**，已被 services/upload.ts 取代）。
- `docs/dm-guide-upload-api.md`（**重写**，182 行）：完整契约、三条铁律、指纹设计、缺片自愈、CORS ExposeHeaders 要求、7 天生命周期+碎片清理规则、已验证行为对照表。

### 重构验证
- `node ./node_modules/typescript/bin/tsc --noEmit`：src/ 0 错误。
- `npm run build:h5`：944 modules / 31.65s 成功；dist 已打包新路径，旧的 `dm-guide/upload/multipart`、`dm_guide_upload_` 字符串全部消失。
- live 后端 probes：11 项检查全过（含 Content-Type→403、秒传、断点续传、incomplete_parts 409 缺片结构均符合前端预期）。

### 关键结论（务必记住）
- **约束①**：切片大小一律以后端 init 返回的 `chunk_size` 为准（本地 CHUNK_SIZE 只是期望值，分片数超 10000 时后端会上调）。
- **约束②**：PUT 分片绝不设 Content-Type。`part_content_type` 是 schema 注释误导，oss.presign_part() 实际没传 content_type，签名不含该头。
- **约束③**：断点续传服务端负责，不再用 localStorage 存 uploadId/ETag。
- `complete` 只回 FileInfo 不含 URL，必须再调一次 download-url。
